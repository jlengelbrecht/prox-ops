# Qwen3.6-27B: A5000 (cluster) vs RX 7900 XTX (edge) — physical validation

EPIC-035 Story 35.7. Measurements taken 2026-08-20 on the live cluster and the CachyOS edge host.

**This report replaces assumptions with measurements. It does not recommend a new
`timeouts.request`** — see [Recommended timeouts](#recommended-timeouts).

## Method

### What was measured, and how the two placements differ

The two cold measurements are **not the same work**, and are never presented as one figure:

- **Edge cold** is *runtime-cold / VRAM-cold*: the model artifact is already resident on local
  storage, llama-swap is running, the interactive guard is SERVING, the model is absent from
  `/running`, and the GPU is at its unloaded baseline (849 MiB measured). It is **not**
  machine-cold and **not** filesystem/storage-cold — both reset paths leave the OS page cache warm,
  so no storage-cold claim is made.
- **KServe scale-from-zero** (NOT "GPU-cold") additionally includes platform lifecycle work: pod scheduling, container start,
  Knative/KServe initialization and GPU runtime initialization, before any model load begins.

The correct comparison between them is therefore **operational cold-start latency** — what a caller
experiences from each placement. **It is not a hardware comparison**, and nothing here supports a
GPU-vs-GPU claim.

### Cold preconditions

- **KServe — deployment-zero / scale-from-zero.** Natural scale-to-zero only. A trial counted only
  when the predictor was **observed at `replicas=0` immediately before the request**. No pod
  deletion, no retention mutation, no forced teardown.

  **This condition is deliberately NOT called "GPU-cold".** This campaign proved that `replicas=0`
  does **not** necessarily mean VRAM has been released (finding F1): a terminating pod can still
  hold ~16 GB while the deployment already reports zero. Every KServe figure in this report is
  therefore a *scale-from-zero* measurement against an observed deployment state, not a measurement
  against a known-free GPU.

  **All five KServe trials are retained as valid.** They measure what a real request encounters
  after the defined precondition. The OOM/restart race documented in F1 is part of that behaviour,
  not a reason to discard a sample — learning that deployment-zero is not GPU-free refines what the
  number *means*, it does not invalidate the measurement.
- **Edge**: 1 natural-TTL anchor + 4 commanded-unload trials (`POST /api/models/unload/:model_id`,
  the same unload lifecycle TTL expiry uses). Every commanded trial passed a seven-point
  post-unload proof: unload API 200, model absent from `/running`, VRAM back within the unloaded
  baseline, guard phase `serving`, endpoint healthy, no interactive claim, and no load-capable
  request between unload confirmation and the timed request. `reset_type` is recorded per sample.

### Instrumentation and its limits

Timings are client-measured via the harness (`edge/benchmarks/bench.sh`), which issues a **streaming**
chat-completions request and records curl's `time_starttransfer`. **`ttft_s` is therefore
time-to-first-response-byte of the stream**, which in practice is the first SSE chunk — typically a
role delta that precedes the first non-empty content token by one chunk. It is not timestamped at the
first content token, and the sub-chunk difference is not resolved by this instrument. Generation and
prompt throughput are server-reported (`timings.*`). The same fixed prompt and generation length were used
for every trial on both placements.

**A readiness decomposition was attempted and is not usable.** `t_pod_ready` was sampled by polling
`status.readyReplicas` every 2s; computed against first token it yields a *negative* residual on
every trial (-1.6s, -3.3s, -2.7s), i.e. first token arrives before the API reports ready. That is
kubelet-to-API propagation lag plus poll interval, not a real ordering.

Consequently: readiness is reported as observed, with its lag, and is **not** used to derive a
scheduling-vs-model-load split. What the data supports is only that essentially the whole cold start
elapses **before** the predictor reports ready, with no meaningful post-readiness component. No
attribution *within* that window is possible from this campaign.

|---|---|---|---|

## Findings

### F1 — CUDA OOM and double container restart when a request arrives at `replicas=0`

**A first-class result of this campaign, not an incident to be footnoted.**

Timeline, UTC 2026-08-20:

| Time | Event |
|---|---|
| 20:33:37.462 | cold trial 5's predictor observed returned to `replicas=0` |
| ~20:33:4x | warm phase issued its untimed warm-up request (ordinary request timing, no mutation) |
| 20:33:53 | `kserve-container` terminated, `reason=Error`, `exitCode=1` |
| ~20:33-20:34 | `Unhealthy` readiness probe 503; `BackOff restarting failed container`; **2 restarts** |
| 20:34:24 | warm-up request finally answered after 41.00s |

The incoming pod could not allocate its weights:

```text
ggml_backend_cuda_buffer_type_alloc_buffer: allocating 16386.94 MiB on device 0:
  cudaMalloc failed: out of memory
alloc_tensor_range: failed to allocate CUDA0 buffer of size 17182947328
llama_model_load: error loading model: unable to allocate CUDA0 buffer
llama_server: exiting due to model loading error
```

**What is proven:** at a moment when the deployment reported `replicas=0`, an incoming predictor
could not allocate ~16 GB on the A5000, terminated with exit 1, and restarted twice
(`kserve-container`: 2 restarts; `queue-proxy`: 0) before a start succeeded. Therefore **`replicas=0`
is not proof that the GPU is free.**

**What is NOT proven:** which process still held the residual VRAM. The campaign captured the
allocation failure and the restart sequence, but **did not capture process-level ownership of the
GPU memory** at that instant — no per-process VRAM accounting was recorded. The outgoing pod is the
natural suspect given the timing, but that attribution is inference, not measurement.

**Consequences.**
- Every KServe residency figure in this report is *deployment-zero*, not *GPU-free*. GPU-free
  residency was not measured and is later than deployment-zero in at least this transition.
- A wake arriving inside the scale-down window can produce a **crash-and-restart**, not merely a
  slow cold start.
- **What the caller actually saw was a slow success, not a failure.** The request returned
  **HTTP 200 after 41.00s**; Knative's activator held the connection across the crash and both
  restarts. **No caller-visible 503 was observed** — every request in this campaign's evidence
  bundle returned 200. The 503s recorded in this finding are **readiness-probe** failures visible in
  cluster events, not responses to a caller. The 41.00s is the visible cost of the path.
- That distinction matters for 35.8's transition drill: on this evidence the failure mode manifests
  as latency absorbed by the activator, not as an error surfaced to the client. Whether that holds
  under the gateway path, and at what concurrency, is what the drill has to establish.

**This report makes no claim that any existing mechanism handles it.** Specifically, it does **not**
assert that R6's health policy and retry configuration absorb this. What must be **evaluated at the
architecture review** is some combination of:
- R6 retry and passive-health behaviour (including whether the retry backoff is sized for a pod that
  is crash-looping rather than merely slow);
- Knative's own request holding / activator behaviour during the scale-down-to-scale-up transition;
- an explicit **scale-down handoff mitigation** that prevents a replacement pod from being scheduled
  onto a GPU whose predecessor has not released VRAM.

Which of these is sufficient — or whether more than one is required — is an open architecture
question this benchmark raises and does not answer.

### F2 — Trial 1's cold start is materially slower, and this campaign cannot say why

Trial 1 measured 122.58s against 39.82-48.58s for trials 2-5. The campaign was **not instrumented
to distinguish** the candidate causes, which include: OS page-cache state for the 17.9 GB artifact,
container/image readiness, filesystem behaviour, Knative/KServe initialization, GPU runtime
initialization, and model-load path differences.

**No cause is selected.** Any page-cache explanation is a hypothesis, not a finding. Establishing it
would need a campaign designed to vary one factor at a time.

The practical implication stands regardless of cause: **the first wake after a long idle period is
substantially more expensive than subsequent ones**, which a single sample would have hidden
entirely.

### F3 — Speculative decoding (MTP) works on ROCm

`--spec-type draft-mtp --spec-draft-n-max 2` is active on the edge, with a draft acceptance rate of
**0.79** measured consistently across all five cold trials. This confirms and refines the 0.91-0.95
figure observed during 35.6 bring-up under different conditions.

## Recommended timeouts

**`timeouts.request: 240s` remains PROVISIONAL. This report does not propose replacing it.**

Five samples are too few to establish a tail, and the observed maximum (122.58s) comes from the one
trial whose cause is undetermined (F2). Reducing the timeout toward that maximum would optimize
around a tiny dataset and re-introduce exactly the assumption this story exists to remove. F1 also
shows a failure mode where a wake does not merely run long but crashes and retries, so timeout alone
is the wrong instrument.

**Capacity / idle-retention:** retention is stable and matches configuration on both placements — **~31.2 min
cluster (last request -> deployment zero)** and ~30.1 min edge (last request -> TTL unload). These figures inform the capacity model and
idle-retention policy; they are **not** inputs to agentgateway's `eviction.duration`.

**The cluster figure must not be read as the A5000 resource-release time.** Per F1, GPU-free
residency is unknown and later than deployment-zero. Any capacity model that treats 31.2 min as the
point the A5000 becomes available for another workload is unsupported by this data.

## Threats to validity

- **Sample size.** N=5 per cold set. Adequate to show that cluster cold-start variance is large and
  edge variance is small; **not** adequate for tail statistics. No p95 is reported for any set.
- **Request paths differ.** The cluster was measured through a port-forward to `kourier-internal`;
  the edge through its production HTTPS + bearer path. Neither goes through agentgateway, so no
  gateway overhead is included on either side.
- **Shared workstation.** The edge host is an interactive desktop. Guard phase was `serving` before
  and after every trial; any trial overlapping a withdrawal would have been discarded. None were.
- **Cluster co-tenancy.** `k8s-work-10` hosts other scale-to-zero InferenceServices. None were
  observed active during the campaign, but this was not enforced.
- **One contaminated sample was excluded**, not counted: an early trial whose cold state was produced
  by a route-discovery probe hitting a live `GET /unload` endpoint rather than by TTL expiry.
  Preserved verbatim as `raw/DISCARDED-probe-contaminated.jsonl`.

  **Note on that file:** the record inside still carries the harness's own
  `"discarded": false`, because the harness had no way to know its precondition was contaminated.
  **The quarantine is external — by filename only — and the raw record is deliberately left
  unmodified.** Do not read the in-record flag as agreement that the sample is usable; do not
  "fix" the file to match its status.
- **Edge natural-TTL expiry has N=1.** By ruling, the remaining edge resets were commanded.
- **Thermal/power behaviour was not characterised.** Sustained runs were 11 minutes; no long
  soak was performed.

## Invariant 7 evidence

KServe scale-to-zero was preserved throughout. Every wake was deliberate and timestamped; each is
recorded in Dimension 1 with its observed-zero timestamp, and each returned to zero (Dimension 2).
No pod was deleted, no retention period altered, no InferenceService modified.

**Final natural scale-down observed 2026-08-20T21:17:11Z**, predictor at `replicas=0`, closing the
campaign. Node `k8s-work-10` reported 11,287 MiB in use afterwards versus 20,040 MiB while the
predictor was serving. Note that this is deployment-state evidence: consistent with release, but per
F1 it is not a direct measurement of VRAM being freed, and no GPU-free timestamp was captured.

Raw samples for every trial, including excluded and metadata records, are preserved under
`edge/benchmarks/raw/`. Three notes for anyone consuming them:

- **They are pretty-printed JSON object streams, not strict line-delimited JSONL**, despite the
  `.jsonl` extension — a naive line-per-record reader will fail. Parse them as a sequence of JSON
  values (e.g. `json.JSONDecoder().raw_decode` in a loop). The harness now writes compact output for
  future runs; these files are left exactly as the campaign produced them.
- **Every cold record carries `"trial": 1`** because each cold trial was a separate single-trial
  invocation. Order by `ts`; the per-trial index, reset type and precondition evidence live in the
  matching `*-meta.jsonl`.
- **Cluster records carry `state_before: "unknown"`** because `--state-cmd` was not used on that
  side. The cold precondition was enforced and timestamped **externally by the campaign** — see
  `t_observed_zero` in `kserve-meta.jsonl` and Dimension 1 — not by the harness's own state check.
