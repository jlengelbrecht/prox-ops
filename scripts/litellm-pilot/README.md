# Isolated OpenCode LiteLLM pilot kit

This Linux-host-only kit prepares an explicit, project-local OpenCode client for offline evaluation. Native credential-file support is limited to Claude Code's Linux JSON record; macOS Keychain is unsupported. It does not qualify a provider or enable `project-router`. The existing LiteLLM GitOps configuration, global OpenCode settings, native logins, and shared review routes are outside this kit.

## Setup

From the repository root, create a new disposable project directory outside any Git worktree. The generator requires a nonexistent output path and refuses symlinked paths, global OpenCode paths, and Git worktrees:

```sh
node scripts/litellm-pilot/generate.mjs --output /tmp/litellm-pilot-client --gateway https://ai-api.homelab0.org/v1 --models anthropic/claude-sonnet-5,chatgpt-gpt-6-luna --model anthropic/claude-sonnet-5 --small-model chatgpt-gpt-6-luna
```

The initial target providers are Claude, ChatGPT/Codex, Grok OAuth, and GitHub Copilot. Claude and ChatGPT are the only explicit candidates today. Grok and Copilot must be onboarded and qualified before their aliases are added to this client or any router. Local LLM integration is deferred; the existing `dub-text` workload is unchanged and stays outside this pilot. The deployment's `XAI_OAUTH_TOKEN_DIR` setting only names where a Grok login would persist. It does not mean a login, access, or subscription billing has been tested.

Run OpenCode inside that directory and select an explicit `litellm-pilot/<alias>` model. Omit any alias not authorized on the scoped pilot virtual key. The key must be owned by the pilot user, limited to those explicit aliases, and have per-key rpm and tpm limits as well as any applicable budget ceiling. Dollar budgets do not bound zero-priced subscription traffic. An empty LiteLLM key model list is unsafe because it permits metered aliases. Supply `LITELLM_PILOT_KEY` from an approved secret source in the local client environment; do not write its value into configuration, shell history, prompts, or reports. Never use the LiteLLM master key. No key is created by this offline kit.

The generated `opencode.json` contains a key reference, a pinned HTTPS gateway, and only the selected models. `--model` and `--small-model` must each name a supplied allowed alias; the example makes no quality or ranking claim. The config enables only `litellm-pilot` even when OpenCode merges other configuration. It denies tools by default, allows project-file read/edit/search/list operations, and explicitly denies shell, subagents, and external-directory access. It requests denial of model edits to its own config, plugin, package, instruction, and environment files; effective path matching must be tested before live use. Use only a trusted synthetic task fixture. Do not add network or external tools or automatic helper agents. Validate all inherited and effective settings before live use. Its `.opencode/plugins/claude-bearer.js` plugin reads the native Claude Code access record immediately before each explicit Claude request. Native JSON parsing briefly loads the whole record, including the refresh field, into process memory; the reader immediately projects the access token and expiry. It never uses, writes, or discloses the refresh token. Claude Code alone owns login, refresh, and storage. The plugin sets provider `Authorization` separately from the gateway's `x-litellm-api-key`. A missing, stale, or malformed record fails with a fixed redacted error. Both `project-router` (proposed) and the existing `smart-router` are denied, as are all aliases outside the explicit allowlist. Every request identified as pilot traffic checks the target URL and actual outgoing scoped-key header. Unexpected provider identities and credential headers fail closed. The hook rejects known destination-override fields in its input, but cannot control downstream gateway behavior, redirects, or other plugins in the same process. The plugin cannot identify a LiteLLM master key by its shape; the operator must supply a scoped virtual key.

The installed OpenCode binary was 1.19.5 at inspection on 2026-11-05; its installed plugin type package was 1.18.29. The offline hook test does not prove that the binary executes the hook or that LiteLLM forwards the bearer correctly. Claude Code may leave an access token expired while idle; rereading the record is not subscription renewal. The live pilot must establish hook loading, effective provider selection and effective tool permissions after config merge. Capture the actual hook input/output shape without credentials, verify that its outgoing headers contain the scoped gateway key, and attempt denied edits of the generated plugin and configuration from the generated non-Git project. Use an isolated configuration home and verify that global plugins, MCP definitions, and instructions are not inherited unintentionally. Application permissions are not an OS sandbox; the OpenCode process and plugins still share access to the pilot key environment and may read the native credential record. File modes and edit rules do not isolate code running with the same OS identity. Use only trusted pilot tasks until that boundary is qualified. The pilot key and Claude record remain sensitive in that process.

## Offline check

```sh
node --test scripts/litellm-pilot/tests/*.test.mjs
```

The suite uses temporary synthetic records. It makes no network calls and does not read real login state.

## Live qualification still required

Before live calls, restore supported DNS and read-only cluster tooling; verify running LiteLLM version/config, exact aliases, scoped key, account identity, per-key rpm/tpm limits and any budget ceiling. Freeze the task fixtures and request/token limits in the pilot qualification contract. Test OpenCode 1.19.5 hook execution, then Q1 explicit provider responses and provenance, Q2 tool loops and resume, Q3 observed native renewal/concurrency/revocation and destination isolation, Q4 actual automatic routing including Claude, Q5 measured task outcomes, and Q6 key/cache/review/rollback/recovery. In Q3 inspect whether client-supplied `api_base` changes the gateway's provider destination; in Q6 isolate or disable cache for revocation evidence and check caller separation. In Q3 confirm that Authorization values are absent from gateway logs and that the gateway strips `x-litellm-api-key` before upstream forwarding, rejects client destination overrides, and does not redirect a scoped key across origins. In Q1 verify the exact Anthropic request/header protocol before expanding calls. Verify the gateway's Claude route accepts this experimental client before any production change. Initial qualification is limited to eight bounded inference calls with no metered fallback. Do not infer Q3 or Q4 from a text response. Until all Q1–Q6 and all four provider classes qualify, the unified pilot is unqualified.

## Rollback

Stop the isolated OpenCode session, remove only the generated pilot project directory, and unset the local pilot-key environment reference. Inspect and remove only this pilot session's OpenCode history and logs from its data directory as needed; do not delete other sessions. Block or delete only the scoped pilot virtual key through its owner if it was created. Any later GitOps pilot alias change has its own reviewed revert. Leave global OpenCode configuration, Claude Code login, LiteLLM PVCs, existing review routes, and other users untouched. Native logout or provider revocation controls subscription access; recovery is a new native login followed by a fresh read.
